# R3.2 — Local Style Authoring

**Status: IMPLEMENTED OFFLINE — live acceptance pending on an owner-confirmed disposable Figma file.**

R3.2 is the local-style phase of R3: paint, text, effect, and grid style lifecycle
and attachment work. It follows R3.1's `set_fill_style` measurement surface; it does
not make R3.1's preview tools stable and it does not authorize a runtime change by
itself.

The owner approved all four safety decisions on 2026-08-26. The implementation is the
R3.2 / `1.20.0` additive-preview surface: `get_local_style`,
`create_or_match_local_style`, `update_local_style`, `get_node_style_attachment`,
`set_local_style_attachment`, and `delete_local_style` (86 tools total). It is not yet
live-accepted, does not promote R3.1 previews, and does not authorize a fake re-pin of
earlier live gates.

## Boundary

R3.2 owns only local Figma style resources and their direct node attachments:

| Style kind | Lifecycle value | Attachment scope |
| --- | --- | --- |
| Paint | `paints` | Fill; stroke attachment is admitted only if its async setter and direct readback pass the same gate design. Existing `set_fill_style` remains its own compatible surface. |
| Text | the already-supported typography value grammar | Text-capable nodes only, with mixed runs reported rather than flattened. |
| Effect | the already-supported `set_effects` grammar | Nodes with the native effect-style attachment surface. This is the phase that closes the effect-style detachment premise. |
| Grid | `layoutGrids`, after a dedicated value-schema probe | Nodes with the native grid-style attachment surface. |

Out of scope: remote/team-library inventory or import, publishing, library keys,
style ordering/folders, style-to-variable binding writes, Code Connect, components,
consumer tokens, OpenDesign mappings, and a generic document mutation compiler. A
new command must use the existing value grammars where one already exists; it may not
invent a second spelling for paints, text values, or effects.

## 1. Local-identity rule

1. A style mutation starts with an exact `{kind, styleId}` resolved from the matching
   current-file local inventory. `figma.getStyleByIdAsync()` may diagnose a rejected ID,
   but it is never sufficient authorization to mutate it.
2. An explicit ID is authoritative: missing, wrong-kind, or non-local IDs refuse. They
   never fall through to a name lookup, an `identityKey` lookup, or a create.
3. A style's Figma `key` is diagnostic only. It is never a mutation selector or a
   cross-file identity mechanism.
4. Exact local name is not ownership. Every create or create-or-match request requires a
   non-empty opaque `identityKey`; a same-kind name collision that does not carry that
   exact key refuses rather than being matched or overwritten.
5. A create-or-match resolution is: explicit local ID first when the operation permits an
   existing resource; otherwise exactly one same-kind local resource bearing this plugin's
   exact private key; otherwise a create only when no same-kind name collision exists.
   Zero, duplicate, unreadable, or conflicting key states refuse before creation. The key
   is byte-for-byte opaque, is not echoed in a receipt, and is never treated as secret
   material. A create-or-match request that supplies both an ID and an `identityKey` must
   verify that exact stored key; it cannot claim or overwrite an unkeyed/differently keyed
   user style through the ID branch.
6. A successful create-or-match receipt names `created`, `matchedBy`, local `id`,
   `kind`, and an `identityKeyStatus`; it does not pretend that a Figma style ID is
   portable across files.
7. Before a public create-or-match path is written, the fork must prove on all four
   style classes that private plugin data can be stored and read back. If a class lacks
   that usable surface, R3.2 does not publish its create capability; the plan does not
   silently downgrade its identity or cleanup guarantee.

## 2. Remote-refusal rule

1. Lifecycle operations act only on a style returned by the matching
   `getLocal*StylesAsync()` inventory in the connected file. Local inventory is an
   authorization boundary, not merely a convenience read.
2. When an ID resolves to `remote: true`, return a typed `remote_style` refusal before
   calling a style setter, node attachment setter, `remove()`, import, or create fallback.
   When the runtime cannot classify an absent ID safely, return `not_exact_local_style`;
   uncertainty never grants a write.
3. Remote `key`, file/library identifiers, remote value snapshots, and import/publish
   APIs are excluded from every R3.2 schema. A similarly named local style is never a
   substitute for a remote input.
4. Replacing or clearing a *node's* existing remote binding with a verified local style
   is allowed: it changes the local node reference, not the remote resource. Its receipt
   must report the prior reference and must not describe that action as a remote-style
   mutation.
5. Offline tests must spy on every native mutator and prove a remote refusal reaches none
   of them. Live acceptance needs a real remote-style control per supported class when
   the owner-confirmed disposable file can supply one. Its absence is `unmeasured`, not a
   fabricated remote ID or a passing safety claim.

## 3. Cleanup and deletion rule

1. Style resources are document-scoped; deleting a scratch page does not clean them up.
   Therefore no R3.2 create capability ships without an owned local deletion path in the
   same phase.
2. A public deletion requires literal `confirm: true`, exact local same-kind resolution,
   and an ownership check against the supplied `identityKey`. It never deletes an
   unrelated same-named user style and never cascades through nodes, styles, variables,
   or components.
3. Before deletion, the handler must obtain a current consumer observation and refuse if
   any consumer remains. A live gate may detach only its recorded scratch consumers, then
   must observe none; an ordinary caller never gains a hidden cascade through user nodes.
   If the consumer observation is unavailable, it returns a typed unavailable-observation
   result rather than relying on Figma's implicit detach behaviour.
4. A delete receipt may say `removed` only after it names an independent post-removal
   signal (for example, a fresh matching local inventory no longer contains the ID). If
   no signal can distinguish deletion from a no-op, it returns `removal_unconfirmed` and
   a re-read instruction rather than a success claim.
5. Every live gate captures a sorted baseline of all four local style inventories and its
   page/current-page state before the first mutation. In `finally` it detaches only its
   recorded scratch consumers, deletes only its recorded owned styles, deletes its scratch
   page, restores the original page, and records every cleanup result.
6. A `finally` attempt is not proof of cleanup. A fresh, separate client session must
   compare the final local-style inventory and page baseline with the original one. Any
   mismatch fails the gate and leaves the exact owned IDs in the report for manual repair.
   R3.2 has no `--allow-permanent-*` flag.

## 4. Observation rule

1. The present shallow `get_styles` inventory is not enough to confirm lifecycle writes.
   R3.2 must first define one bounded canonical local-style read projection: exact local
   ID, kind, name, applicable stored value, remote/local status, value-readability, and
   the direct style-reference/consumer observations needed by the operation. It may be an
   additive extension or a new exact read; that naming choice is deferred.
2. Create and update receipts carry distinct `before` and post-write `after` projections,
   `readbackMatchesRequested`, and `outcome: confirmed | unconfirmed`. Figma-normalized
   values are reported as read, never replaced with the request payload.
3. Attachment success needs a second observation path that reads the plugin-node style ID
   directly. REST export `styles` keys and absent fields are not interchangeable with
   plugin style IDs. Mixed, absent, and unreadable references remain distinguishable.
4. The effect gate must attach an owned local effect style, use the existing effects
   mutation as its controlled change, and read whether the reference detached. An
   unstyled target can only yield `unmeasured`; it cannot close the effect-detachment
   premise.
5. The grid value/attachment path is gated by a dedicated platform probe before its
   public grammar is frozen. A Figma default, a mocked array, or a round trip through the
   same setter is not proof that a grid value was retained.
6. Offline fixtures must include known-bad paths: a remote resource, wrong kind, duplicate
   identity key, setter that accepts and discards a write, stale/deferred deletion read,
   and a consumer observation that fails to vary. A green fixture that cannot fail under
   one of those conditions is not acceptance evidence.
7. `refused`, `unconfirmed`, and `unmeasured` are public outcomes, not aliases for
   success. Only a discriminating Figma observation may produce `confirmed` or `removed`.

## Implementation record and remaining acceptance sequence

1. [x] **Offline capability contract.** The harness now supplies mutable local styles,
   private-data, consumer, async-attachment, silent-write, and stale-removal controls for
   all four kinds. The live API facts remain deliberately unclaimed until the disposable
   file run.
2. [x] **Read and identity foundation.** The canonical local-style projection and shared
   local resolution/identity helpers cover every resolution order, collision, kind, and
   remote branch before any mutator is reached.
3. [x] **Lifecycle and attachment slice.** The six R3.2 operations cover local
   create-or-match/update, attachment/clear, and owned deletion. `set_fill_style` remains
   compatible; its stable inputs and receipts were not reinterpreted.
4. [x] **Offline release gate.** The `1.20.0` contract and runtime metadata are generated,
   `dist/` is rebuilt, frozen baselines replay, and killable tests cover all four rules.
   R3.2 results remain `additive-preview`; stability promotion is a later decision.
5. [ ] **Live acceptance.** Use only an owner-confirmed disposable file with
   `--disposable-target=true` and a real `--remote-style-id=<paint-style-id>` control. The
   gate refuses to run without that remote control, then proves bad-runtime refusal before
   the first mutation, per-kind lifecycle/attachment observations, all existing-style
   remote refusals, and separate-session cleanup.
6. **Release replay.** Record the new server/plugin identities, re-pin and execute every
   current live gate plus the R3.2 scenarios on the published pair, then freeze the
   compatibility baseline. A pin edit without execution is not a replay.

## Acceptance matrix

| Scenario | Required discriminating fact | Failure / unmeasured outcome |
| --- | --- | --- |
| Identity | Same request matches only its owned same-kind local style; wrong ID/name/key cannot create or overwrite. | Typed refusal; zero native creates/writes. |
| Local lifecycle | Created or updated value differs from its control and matches a fresh local read. | `unconfirmed`; no promotion. |
| Attachment | Exact local style ID appears on the supported scratch node through a second direct read. | `unconfirmed` or typed unsupported-target refusal. |
| Effect detachment | An owned effect style is attached, then the controlled effects write proves attached versus detached behaviour. | `unmeasured` if no owned attachment exists; not a pass. |
| Remote | A real remote style is refused before every native mutator; a local node's prior remote binding is accurately disclosed if replaced. | `unmeasured` only when no real remote control is available; phase safety claim remains open. |
| Deletion / cleanup | Detached owned style disappears from a fresh local inventory and the separate client sees the exact baseline restored. | `removal_unconfirmed` or gate failure; never a green cleanup claim. |
| Runtime boundary | A bad server/plugin pin exits before baseline creation or any mutation. | Gate failure if a write is reachable. |

## Non-goals and follow-up decisions

- R3.2 does not promote the existing R3.1 preview tools merely because it uses them.
- It does not infer a remote-library inventory from local APIs; absence from a local list
  remains absence of evidence about libraries.
- It does not make a style resource cross-file portable. Cross-file identity and import
  remain the deferred remote/team-library roadmap work.
- It does not add a consumer-specific token, theme, component, or page compiler. Those
  belong to consumers or R3.3 as appropriate.

Approval and offline implementation are recorded above. The only remaining authorization
boundary is live acceptance: run the pinned gate on an owner-confirmed disposable Figma file
with a real remote paint-style control, then re-run the historical gates before changing their
status or promoting any R3.2 result.
