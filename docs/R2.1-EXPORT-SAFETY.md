# R2.1 export safety amendment

**Status: accepted 2026-08-10 — offline gate and connected Figma gate passed.**

This amendment closes the source defect found by R2.0's large-export live gate: a
caller could commit Figma to a rasterization whose cost was invisible beforehand, and
the work continued after the server's 120 s timeout.

## Contract change

`export_node_as_image` now returns a `preflight` block alongside its existing receipt.
For PNG/JPG it estimates the rendered raster before `exportAsync`:

```json
{
  "nodeWidth": 1440,
  "nodeHeight": 900,
  "boundsWidth": 1440,
  "boundsHeight": 900,
  "boundsSource": "absoluteRenderBounds",
  "projectedWidth": 2880,
  "projectedHeight": 1800,
  "projectedMegapixels": 5.184,
  "megapixelLimit": 16,
  "limitApplied": true,
  "costKnown": true,
  "overLimit": false,
  "overrideUsed": false
}
```

`absoluteRenderBounds` is preferred because effects can extend beyond geometry;
`node-width-height` is the fallback. Scale applies to both dimensions. The 16 MP ceiling
is a fork safety policy, not a statement of Figma's maximum supported export.

PNG/JPG requests above 16 MP, or whose bounds cannot be measured, now fail before
Figma begins encoding. `allowLargeExport: true` is an explicit escape hatch for a caller
that accepts the risk. SVG/PDF report the projection but use `limitApplied: false`.

The plugin sends `started` before `exportAsync`, then `in_progress` after Figma returns
bytes and `completed` after base64 preparation. The server retains the 120 s inactivity
budget. If an export still times out, the pair is latched `incompatible`; subsequent
document calls are refused until `get_runtime_info` proves recovery.

## Consumer migration

Existing calls remain schema-valid. The deliberate behavior change is limited to large
or unmeasurable PNG/JPG requests:

1. Prefer a smaller node or lower `scale` until `projectedMegapixels <= 16`.
2. Keep using `filePath` for multi-megabyte output so base64 never enters model context.
3. Use `allowLargeExport: true` only when the caller accepts that Figma cannot be
   cancelled after encoding starts.
4. After any export timeout, call `get_runtime_info`; do not issue another document
   operation while compatibility is latched.

Because this changes existing default behavior above the ceiling, all three contract
identifiers moved `1.2.0` → `1.2.1`; this is not shipped silently under the R2.0
fingerprint.

## Offline evidence

`bun run verify` passes with 47 tests and zero compatibility errors against the frozen
R0 and R1 baselines. New cases prove:

- scale is applied to both dimensions (`100×100 @ 2×` → `200×200`, `0.04 MP`);
- a 25 MP implicit raster request is rejected before `exportAsync` is called;
- an explicit override is present in the receipt and proceeds;
- SVG is not subjected to the raster ceiling;
- progress emits `started` → `in_progress` → `completed`;
- receipt metadata survives server-side hashing/file delivery; and
- an export timeout latches compatibility while other command timeouts do not trigger
  the export-specific latch.

`dist/server.js` and `dist/server.cjs` were rebuilt by the same gate.

## Connected evidence — passed 2026-08-10

[`scripts/live-export-gate.mjs`](../scripts/live-export-gate.mjs) ran against the same
SYD fixture used to find the defect, channel `4g146t0n`. Full machine-readable evidence
was written to `/tmp/talk-to-figma-r2.1-live-ypCKsj/report.json`; the exported PNG is
beside it.

1. The fresh stdio client exposed 49 tools and 6 prompts. `get_runtime_info` verified
   the exact R2.1 server/plugin pair and fingerprint above with `compatible` and zero
   issues before document work.
2. Section `1113:5031` at `scale: 3` was refused in **11 ms**, before encoding:
   `6600×13474` at 3× projected to `19800×40422` / **800.3556 MP**, above the 16 MP
   ceiling. No file existed afterwards. `get_runtime_info` answered in **15 ms** and
   remained compatible.
3. The suggested 0.5× starting point was also honestly refused in **9 ms** because it
   still projected to `3300×6737` / **22.2321 MP**. It wrote no file; the runtime probe
   then answered in **10 ms**. The harness conservatively derived **0.4×** from the
   reported bounds.
4. The 0.4× file-backed PNG completed in **22.550 s**, inside the 120 s budget and
   without an inline image block. Preflight reported `2640×5390` / **14.2296 MP**,
   `overLimit: false`, `overrideUsed: false`. The receipt identified a 1,265,757-byte
   PNG, actual dimensions `2672×5422`, SHA-256
   `5badbae43909eefa1cf1d1dfd7c7acfc5331652a9d29bceec43097bbfa72b4f6`.
5. Independent `wc`, `sha256sum`, and `file` checks reproduced the receipt byte count,
   hash, and `2672×5422` PNG dimensions exactly. The rejected 3× and 0.5× paths remained
   absent.
6. Immediately after the completed export, `get_runtime_info` answered compatible in
   **11 ms** and `get_pages` returned all 6 pages in **16 ms**.

The preflight projection and the encoded dimensions are intentionally separate. This
fixture used the `node-width-height` fallback, while the PNG included pixels beyond that
geometry; the conservative 0.4× choice kept the actual artifact below 16 MP as well.
The source fix and its connected behavior are accepted; the R2 export live gate is
closed.
