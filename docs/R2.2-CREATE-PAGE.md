# R2.2 — `create_page`

First tool of R2's *generic safety and orchestration primitives*. Adds one narrow,
consumer-neutral write: create a page, with an explicit name and an explicit
duplicate-name policy.

**Status: ACCEPTED 2026-08-10.** Offline gate green at 54 tests; connected gate passed on
channel `0bcywzod` against the exact R2.2 pair, with the document restored id-for-id.

New capability ID: `figma.command.create_page@1`. `packageVersion` stays at upstream's

The version bump is not cosmetic. R1 established that **a release which grows the
contract must bump `serverSchemaVersion`, or it ships silently** — the fingerprint covers
`serverSchemaVersion` plus per-command capability IDs. Here a new capability ID would
have moved the fingerprint anyway, but the rule is applied regardless of whether the
change happens to be self-announcing.

## The contract

```
create_page(name, onDuplicate?, index?)
```

| Parameter | Type | Default | Meaning |
| --- | --- | --- | --- |
| `name` | string, required | — | Page name. Whitespace-only is refused. |
| `onDuplicate` | `"error"` \| `"allow"` | `"error"` | What to do when a page with this **exact** name already exists. |
| `index` | integer, optional | append last | 0-based position among the document's pages. Valid range `0..pageCount`. |

Classification: `direction: "write"`, `scope: "document"`, `timeoutClass: "standard"`
(30 s — the cost is O(1), unlike the file-scaled reads that declare `heavy_read`),
`resultStability: "stable"`, `progress.pluginUpdates: "none"`.

### Why `onDuplicate` defaults to refusing

Figma itself permits duplicate page names, so the fork cannot lean on the platform to
decide. The default refuses because the failure it prevents is silent: a consumer
re-running a capture or authoring sequence would otherwise fan out same-named pages, and
notice only later. `"allow"` is one word away, and the refusal names the colliding page
ID so the caller can choose deliberately.

`"reuse"` — returning the existing page instead of creating one — is **deliberately not
supported**. That is idempotency, and `TASKS.md` requires idempotency semantics to be
proven independently of a consumer scene format before they enter the contract. An
offline test asserts `"reuse"` is rejected, so it cannot be added by accident.

### What it deliberately does not do

- **It does not switch the active page.** Creating is not navigating; call
  `set_current_page` afterwards. A regression test pins this, because if it ever changed,
  a consumer's next current-page write would silently land somewhere else.
- **It does not delete or rename.** `delete_node` already removes a page generically
  (`node.remove()` works on a `PageNode`), so the gate cleans up without a new tool.

## Result shape

Captured from an observed reply, not written from prose — the practice R1 adopted after
`figma-to-code` made seven validator corrections against prose docs.

```json
{
  "id": "1234:5678",
  "name": "R2.2 Gate 20260810",
  "index": 6,
  "requestedIndex": null,
  "pageCount": 7,
  "onDuplicate": "error",
  "duplicateNameExisted": false,
  "existingPageIds": []
}
```

| Field | Notes |
| --- | --- |
| `index` | The **observed** final position, read back after insertion. |
| `requestedIndex` | What the caller asked for, or `null`. Reordering an existing child is index-sensitive, so the receipt states both rather than assuming they agree. |
| `pageCount` | Document page count **after** the create. |
| `onDuplicate` | Echoed even when defaulted, so a consumer never has to infer which policy applied. |
| `duplicateNameExisted` | True whenever a same-named page existed — reported on the `"allow"` path too, so repeated runs can detect fan-out. |
| `existingPageIds` | IDs of the pages that already carried the name. |

Refusals carry the standard runtime diagnostic suffix
(`[runtime: server=…, schema=…, plugin=…, compatibility=…]`).

green, and **all three frozen baselines replay at zero errors**: R0, R1, and the newly
frozen `contracts/baselines/r2.1-public-contract.json`. Freezing R2.1 means `create_page`
is checked against the last *accepted* release, not only against R0/R1.

Seven new cases in `tests/create-page.test.mjs`, run against the real `code.js` in the VM
harness:

1. append reports the observed position and echoes the defaulted policy
2. creating does not switch the active page
3. a duplicate is refused by default, naming the colliding ID — and does not mutate
4. a duplicate is created only under `"allow"`, and declares `duplicateNameExisted`
5. an explicit `index: 0` places the page first and shifts the rest
6. `index === pageCount` is accepted as the append position
7. invalid input (empty/whitespace name, `"reuse"`, fractional/negative/out-of-range
   index) is refused, and no rejected call leaves a page behind

Two existing gates fired correctly during this work and were updated rather than worked
around: the frozen tool-count tripwire (49 → 50) and the README-inventory check.

## Connected gate

`scripts/live-create-page-gate.mjs --channel=<channel>` spawns its **own** server from
`dist/server.js`, so the server half cannot be stale. It verifies the exact R2.2 pair
before any mutation, then: append → confirm via `get_pages` → refuse duplicate → confirm
no mutation → allow duplicate → index insert → refuse invalid input → delete exactly what
it created → assert the page list is restored **id-for-id, in order** → re-probe runtime.

**The pair guard is already proven.** Run against the still-loaded 1.2.1 plugin on
channel `4g146t0n` (2026-08-10), a fresh 1.3.0 server refused at `join_channel`, before

the stronger one is invisible from the plugin side:

| Input | Layer | Time | Message |
| --- | --- | --- | --- |
| `name: "   "` | handler | 42 ms | `Missing or empty name parameter` |
| `onDuplicate: "reuse"` | **schema** | **1 ms** | Zod `invalid_enum_value`, `Expected 'error' \| 'allow'` |

After the gate finished, a **separate** MCP client re-read the document and saw the
original six pages unchanged. That independent confirmation is what makes the restoration
claim more than the gate grading its own homework.

### The harness defect this gate found in itself

The first connected run (`/tmp/talk-to-figma-r2.2-live-P4202r/report.json`) reported
`success: false` — and **the product was not at fault.** Steps 1–5 all passed; the gate
then treated the `"reuse"` rejection as a crash, because a schema-level refusal arrives
as a *thrown* MCP protocol error rather than an error *result*, and only the result shape
was handled. The better outcome was being scored as a failure.

Because the abort happened before cleanup, that run left three pages (`6009:9112`–`9114`)
in the document; they were removed and the page list verified back to baseline before the
re-run. `callExpectingRefusal` now accepts both shapes and records which layer refused.

This is the **same class of defect** as the one R2.1's export gate hit, where a derived
`0.5×` scale was still over the ceiling and the honest refusal aborted the harness. Both
times the product behaved correctly and the harness mis-scored it. The standing lesson:
**in a gate, a refusal is a first-class expected outcome, not an exception** — and a gate
that mutates must clean up on the failure path, not only on the success path.

## Consumer upgrade note

**Migration required: none.** `create_page` is purely additive — one new tool, one new
capability ID, no existing tool's schema, scope, timeout class, or result shape changed.
All three compatibility baselines replay clean, so a consumer pinned to R0, R1, or R2.1
keeps working unchanged against the R2.2 runtime.

A consumer that wants the tool must re-pin to the R2.2 pair
(`r2-server-79eb6a3d10d2` ↔ `r2-plugin-3b393bab2224`, fingerprint
`sha256:3f2407b8…310bb45`) and require a `compatible` preflight before use, exactly as in
R1/R2.1. Pinning the fingerprint alone is sufficient to detect this change, because the
new capability ID moves it — but pin the schema version too, per the R1 finding.
