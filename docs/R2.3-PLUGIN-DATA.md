## The contract

```
get_plugin_data(nodeId, key?, namespace?, limit?, offset?, maxValueBytes?)
set_plugin_data(nodeId, key, value|null, namespace?)
```

`get_plugin_data` is `direction: "read"`, `set_plugin_data` is `"write"`; both are
`scope: "node"`, `timeoutClass: "standard"`, `resultStability: "stable"`. Cost is O(1) in
the node's key count, so neither declares the heavy budget.

### Two stores, selected by one optional parameter

Figma has a private per-plugin store and a namespaced shared store. **Omitting `namespace`
uses the private store; passing one uses the shared store.**

The distinction matters for consumers and is not cosmetic. Private data is keyed to *this
plugin's ID*, so a consumer's own tooling — or the REST API — cannot read it, and a
different plugin build cannot either. Shared data under a caller-chosen namespace survives
both. A consumer that wants to read its own metadata outside this MCP bridge must use a
namespace.

Namespaces are isolated: reading namespace `B` never returns keys written to `A`, which is
what makes "consumers own their conventions" true rather than aspirational.

### Bounding

Three independent bounds, because a node's metadata is caller-controlled and can be large:

- **`limit` / `offset`** page the key list (default 100). `keyCount` stays a **whole-node
  total** regardless of the window — the same count-vs-window separation `get_node_variables`
  uses.
- **`maxValueBytes`** (default 10000) truncates an oversize value *in the reply* while
  still reporting its true `bytes`, so a caller always knows what it did not receive.
- **`set_plugin_data` refuses above 100000 bytes**, Figma's documented per-entry ceiling,
  with a message naming the limit rather than letting the platform throw opaquely.

`complete` is false whenever anything truncated, and `limitations[]` says which bound
fired.

Sizes are counted in **UTF-8 bytes, not UTF-16 code units** — `"é→😀"` is 9 bytes, not the
5 units a naive `.length` reports. That was verified against a real Figma write, not only
against the offline stub.

### Absent vs. empty — and why `""` is refused

Figma returns `""` for a key that was never set, which is indistinguishable from a stored
empty string. `get_plugin_data` therefore tests **membership** and reports `present`, so
the ambiguity never reaches the caller.

⛔ **`set_plugin_data` refuses `value: ""`.** This is a correction made during
implementation, and it is worth recording because the original design was wrong.

The intent was: `null` deletes, and an empty string stores an empty string — so a consumer
legitimately storing `""` could not erase a key by accident. **The second half is not
implementable.** Figma *defines* writing `""` as removal; there is no separate delete call
and no way to store an empty value. An offline test written to assert the intended
behavior failed, which is how the mistake was caught before it shipped.

Three options were possible, and only one is honest:

| Option | Why not |
| --- | --- |
| Mirror Figma — `""` deletes | Reintroduces exactly the silent-deletion footgun the contract set out to remove. |
| Encode `""` as a sentinel | Fork-invented magic that corrupts the shared store for every other reader — the REST API and other plugins would see the sentinel, defeating the point of shared data. |
| **Refuse `""`** ✅ | Keeps `null` the single, explicit spelling of delete. The caller learns the platform constraint at the boundary instead of discovering a missing key later. |

The refusal names the key and the remedy:

> `Figma removes a key when it is written the empty string, so "" cannot be stored. Pass value: null to remove "capture-id" explicitly, or store a non-empty placeholder`

Removing a key that was never there returns `operation: "noop_absent"` rather than
claiming a removal that did not happen.

Captured from observed live replies.

`get_plugin_data`:

```json
{
  "nodeId": "6009:9118",
  "nodeName": "R2.3 Gate 20260810164457",
  "nodeType": "PAGE",
  "store": "private",
  "namespace": null,
  "requestedKey": null,
  "keyCount": 1,
  "entries": [
    { "key": "capture-id", "present": true, "value": "run-7", "bytes": 5, "truncated": false }
  ],
  "pagination": { "limit": 100, "offset": 0, "returned": 1, "hasMore": false },
  "maxValueBytes": 10000,
  "complete": true,
  "limitations": []
}
```

`set_plugin_data`:

```json
{
  "nodeId": "6009:9118",
  "nodeName": "R2.3 Gate 20260810164457",
  "nodeType": "PAGE",
  "store": "shared",
  "namespace": "r2_3_gate",
  "key": "capture-id",
  "operation": "set",
  "existed": false,
  "previousBytes": null,
  "bytes": 12,
  "keyCount": 1
}
```

`operation` is one of `set` / `removed` / `noop_absent`. `previousBytes` is the size of
the value that was overwritten, or `null` when the key did not exist.

## Consumer upgrade note

**Migration required: none.** Both tools are purely additive: two new tools, two new
capability IDs, and no change to any existing tool's schema, scope, timeout class, or
result shape. All four baselines replay clean, so a consumer pinned to R0, R1, R2.1, or
R2.2 keeps working unchanged.

To use them, re-pin to `r2-server-f152fb666599` ↔ `r2-plugin-8dc3783f024f`, fingerprint
`sha256:c3cd6e71…dcc6bd`, and require a `compatible` preflight before use.

**Choosing a store:** if your own tooling needs to read the metadata back — outside this
MCP bridge, via the REST API, or from a future fork build — use a `namespace`. The private
store is bound to this plugin's ID and nothing else can see it.
