# R2.4 — `apply_batch`, the generic batch operation contract

Last item of `TASKS.md`'s *"generic page/metadata/batch"* line. Applies many node
mutations in one call, against node IDs that already exist, with a typed per-operation
receipt. Design and rationale: [`BATCH-CONTRACT-PLAN.md`](BATCH-CONTRACT-PLAN.md).

**Status: Phases 1 and 2 BUILT; the 5.5 live gate PASSED 2026-08-12; NOT yet accepted.**
`apply_batch` stays `resultStability: "additive-preview"`. The R1 precedent is that a tool
is promoted to `stable` at acceptance, not at registration — and acceptance still owes
3.1/3.2 (chunked progress and the measured sleep default), Phase 4 (additive alignment of
the three shipped batch tools) and 5.6.

New capability ID: `figma.command.apply_batch@1`. `timeoutClass: "heavy_batch"` (rank 4 —
a batch scales with its *arguments*, not with the file). `pluginUpdates: "none"`, which is
true today and is also what currently gives the batch a real ceiling, since nothing resets
the inactivity timer.

## The contract

```
apply_batch(operations[], onError?, prevalidateOnly?, timeBudgetMs?, maxResultBytes?)
```

Every target is resolved in one **total** pass before anything is written, so
`onError: "stop"` refuses the whole batch without mutating and `prevalidateOnly` is a real
dry run. v1 is **mutate-only**: an operation may only name a node ID that already exists,
and every `create_*` is pinned absent by a test.

Two refusals **throw** instead of returning a receipt — a duplicate `id` makes correlation
undefined, and an unknown `op` has no entry shape, so neither can be reported inside the
structure it breaks. Everything below the envelope is reported *in* a well-formed receipt.

⛔ **Operations are NOT atomic.** Nine of the fifteen allowlisted mutations write more than
one field. A `failed` receipt carries `partialApplicationPossible` and, when true, the
recorded reason — so a caller re-reads the node instead of assuming its request was a
no-op.

### Total prevalidation, observed on real content

The dry run resolved real node `9:2` ("Frame 1", `FRAME`) on page `0:1`, reporting
`childCount: 1` for **a `delete_node` operation it did not perform** — D7's blast-radius
promise, observed on a node we were not willing to lose. The scratch leaf resolved to
`childCount: null`, not `0`: *"cannot have children"* is not *"has none"*. Re-reading the
real page afterwards found the node present and its name unchanged, so `prevalidateOnly`
wrote nothing.

### Atomic refusal, then honest partial

The same three operations — a rename, a `set_fill_color` at a nonexistent id, a text write
— were submitted twice. Under `stop` the batch was refused whole (`node_not_found` on the
bad target, every operation `skipped`) and read-backs confirmed the rect was still
`gate-probe-rect` and the text still `before`. Under `continue` the unresolvable target was
skipped and the other two applied, confirmed by read-back. The bad target sat in the
**middle** of the batch, so prevalidation totality does not depend on ordering.

### The two envelope refusals arrive differently

- **Duplicate `id`** — the plugin throws; the tool wrapper catches it into an error
  *result*. Recorded layer: `handler`.
- **Disallowed `op`** — the tool's inline `z.enum` rejects it before dispatch, so it is a
  genuinely thrown protocol error listing all fifteen allowed operations. Recorded layer:
  `schema`.

`BATCH_ERROR_CODE_DELIVERY` calls both *"thrown"*, which is true at the module boundary;
through this transport only the second is literally thrown. A result-only harness would
mis-score both, which is why the gate records the layer instead of flattening it.

### Non-atomicity is now observed, not just declared

All three probes reproduced a partial application against a real file, in one `continue`
batch that still reported `complete: true`:

| --- | --- | --- |
| `set_item_spacing` | child gap 16 → **24** | the handler's own `layoutWrap !== "WRAP"` check |
| `move_node` | `x` 0 → **120** | Figma: *in set_y: Property "y" failed validation: Expected number, received string* |
| `set_stroke_color` | `strokes` none → **SOLID `#ff0000`** | Figma: *in set_strokeWeight: … Expected number, received string* |

⭐ **Two of the six *unproven* non-atomic operations are now proven.** `move_node` and
`set_stroke_color` were listed rather than demonstrated, on the stated hypothesis that *"a
platform-level rejection on a later field leaves the earlier ones applied."* Both now
reproduce exactly that, at the Figma property setter rather than in fork code — the
hypothesis is observed, not assumed. Five of the nine are now proven.

⚠️ `itemSpacing` has **no read path**: both copies of `filterFigmaNode` drop it, so no tool
surfaces it. The gate reads it back indirectly as the gap between two auto-layout children,
whose `absoluteBoundingBox` does survive the filter.

Truncation was exercised in the same batch: `maxResultBytes: 8` cut the succeeding
operation's result while still reporting its true size (`resultBytes: 77`,
`resultTruncated: true`).

## What the gate found

1. 🔴 **The `apply_batch` description is wrong about `params`.** It claims *"Same shape as
   the standalone tool of the same name"*, but batch params go straight to the plugin
   handler: `set_fill_color` and `set_stroke_color` take `{color:{r,g,b,a}}` in a batch and
   flat `r,g,b,a` as standalone tools. A caller copying tool arguments into a batch
   operation gets a runtime failure. ⛔ Fix it with 3.1, which re-pins the pair anyway —
   editing it now would move the build the gate just pinned.
2. **`params` is `z.record(z.any())`, so per-operation arguments get no schema
   validation.** A wrong-shaped param fails plugin-side and arrives as a receipt entry
   rather than a schema throw. Defensible for a batch — a receipt beats an exception — but
   it is a real asymmetry with the standalone tools and belongs in the description.
3. **`operation_not_allowed` is unreachable through this transport.** The allowlist is
   enforced twice and the outer layer answers first, so the plugin's own check never
   refuses a live consumer. The code stays because the plugin is reachable by other
   clients, but no consumer will observe it here.
